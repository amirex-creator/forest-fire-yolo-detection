# 分批递进训练记录（阶段六）

> 本文件记录**真实执行**的分批训练。每一批都要先跑、再看指标、再等人工决定是否继续。
> 没有跑过的批次不会出现在"执行记录"里；任何数字都来自 `outputs/reports/` 下的原始报告。

---

## 一、为什么分批，而不是一次跑 50 轮

1. **显存只有 6 GB**：batch/AMP 一旦不稳，长跑中途 OOM 会浪费几个小时。
2. **指标要能追溯**：一次跑完，中间过程无法复核；分批可以在每批留下完整的权重、曲线和报告。
3. **避免"改完参数就忘"**：每批参数都写在报告里，论文里能对得上。
4. **累计轮数有上限**：防止无意中把 30 轮跑成 300 轮。

## 二、批次协议（`train.py` 已实现）

| 项目 | 规定 |
| --- | --- |
| 每批轮数 | 由 `--epochs` 指定，一批一停，不自动追加 |
| 累计上限 | 默认 **30 轮**，写死在 `TOTAL_EPOCH_BUDGET_DEFAULT`，超过直接拒绝启动 |
| 台账文件 | `outputs/reports/training_ledger.json`，记录每批 run 名、轮数、状态、mAP、起止时间 |
| 训练前快照 | 对 train/val/test 全部图片算 sha256，写 `image_snapshot.json`（约 107 秒） |
| 训练后对比 | 只对 size/mtime 变化的文件重算 sha256，把**真的被改写**的图片列进报告 |
| OOM 策略 | `--no-downgrade`：显存不足**立即终止**并退出码 4，不再自动降 batch 重试 |
| 续训 | 用 `--weights models/<上一批>_last.pt` 起步；**不改**数据集、yaml、随机种子 |
| 每批产物 | `best.pt` / `last.pt` / `results.csv` / `results.png` / 混淆矩阵 / `.json` + `.md` 报告 |
| 过拟合判断 | 取最近 3 轮 train/val box_loss 与 mAP50 的走向，给出可观测趋势（不是统计检验） |

### 常用命令

```powershell
# 第一批（已完成，见下）
.\.venv\Scripts\python.exe train.py --full --epochs 10 --workers 1 --batch 8 --imgsz 640 --device 0 --no-downgrade --name batch1_e10

# 后续批次（模板，仅在确认要续训后执行）
.\.venv\Scripts\python.exe train.py --full --epochs 10 --workers 1 --batch 8 --imgsz 640 --device 0 --no-downgrade --weights models/batch1_e10_full_<时间戳>_last.pt --name batch2_e10

# 查看累计轮数（台账）
Get-Content outputs\reports\training_ledger.json
```

### 过拟合判断

- 结论：**暂无明显过拟合迹象**
- 依据：最近 3 轮 train/box_loss 1.637 → 1.529 下降，val/box_loss 1.183 → 1.128 同步下降，
  mAP50 0.589 → 0.628 → 0.653 仍在上升。
- 注意：val/box_loss（≈1.13）**低于** train/box_loss（≈1.53），这在 YOLO 里很常见
  （训练时带数据增强，验证时不带）。这**不是**过拟合的证据，也不能当成"验证比训练更准"的结论。

## 四、第一批的结论（只基于上述真实数字）

1. 10 轮训练稳定完成，显存与内存都在安全范围内，没有 OOM。
2. 指标仍在单调上升（第 10 轮 mAP50 0.653），**没有到平台期**，说明继续训练还有空间。
3. 烟雾检测效果好于火焰检测，两者差距约 0.12 mAP50。
4. 以上都是 **val 集**数字。**test 集尚未使用**——它要留到阶段八做一次性最终评价，不能拿来调参。
