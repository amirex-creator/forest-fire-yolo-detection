## 二、试跑前发现并修掉的三个真实问题

### 问题 1：`fraction` 让试跑变成"只学空白"（最关键）

第一次试跑用 `fraction=0.1`（Ultralytics 的"只用 10% 数据"参数），结果两个 epoch 的
`train/box_loss` 只有 0.075 / 0.064，`mAP50` 恒为 0，`train_batch0.jpg` 里 8 张样本
**一个标注框都没有**。

排查后确认根因在 Ultralytics 的实现：

```python
# ultralytics/data/base.py:224（实测版本 8.4.190）
im_files = sorted(im_files)                      # 先按文件名排序
count = max(1, round(len(im_files) * self.fraction))
im_files = im_files[:count]                      # 再取前 count 张
```

**`fraction` 取的是"按文件名排序后的前 N 张"，不是随机抽样。**
本数据集文件名已重编号（`AoF00000.jpg`、`AoF00001.jpg`…），排序后的前 1,507 张里：

- 空标签负样本 **1,502 张**
- 有标注框的只有 **5 张**

于是模型只看到"没有任何目标"的画面，自然学会预测空白，指标全 0。
这不是模型能力问题，是**抽样方式造成的假象**。

**修法**：不再用 `fraction`。新增分层抽样函数 `build_trial_train_list()`：

- 按"有框 / 空标签"的真实比例（全量 train 空标签率 **43.08%**）抽 N 张；
- 输出清单 `trial_train.txt`（绝对路径，一行一张）；
- 运行时 data yaml 的 `train:` 指向该清单，`fraction` 强制 1.0；
- 种子固定（`seed=0`），可复现。

重跑后 `train_batch0.jpg` 里能看到真实标注框，`box_loss` 从 0.075 回到 **2.34**（正常量级）。

### 问题 2：`configs/forest_smoke.yaml` 的许可证行让 YAML 解析失败

第 38 行原本是 `license: CC0: Public Domain`，**值里带冒号却没加引号**，
`yaml.safe_load()` 直接报 `mapping values are not allowed here`。

这行从阶段三就存在，但阶段五的检查工具只读自己生成的 JSON，从未加载这个 yaml，
所以一直潜伏到训练脚本第一次读它才暴露。

**修法**：改成 `license: "CC0: Public Domain"`，并用 venv 里的 PyYAML 复核
`nc=2`、`names=[smoke, fire]` 正常。

### 问题 3：Ultralytics 会就地改写数据集图片

训练时 Ultralytics 报 `corrupt JPEG restored and saved`，随后**直接把原图重写**。
本次运行中被改写的文件：

| 集合 | 文件数 | 说明 |
| --- | --- | --- |
| train | 8 张 | `WEB06626 / WEB07271 / WEB07297 / WEB07552 / WEB07555 / WEB07561 / WEB11315 / WEB11319` |
| val | 5 张（上一轮留下的记录） | `WEB07540 / WEB07541 / WEB07554 / WEB11316 / WEB11323` |

**修法**：`train.py` 新增 `scan_modified_images()`，训练结束扫描全部 21,527 张图片的
mtime，把训练期间的改动写进报告（本次报告里 `modified_count: 8`）。
这样"数据集被悄悄改了"这件事至少有记录。

> 注意：这些图片是**内容被修复后覆盖**的，原始字节已不可恢复。
> 如果要严格留档，应在训练前做一次哈希快照（阶段八评价前会补这一步）。

## 四、结论（只到这里为止）

1. **训练链路是通的**：数据校验 → 加载预训练权重 → 训练 → 验证 → 保存权重/曲线/报告，全部真实跑通。
2. **损失与指标方向正确**：box/cls loss 下降，mAP50 从 0.052 升到 0.181，说明模型确实在学东西。
3. **2 个 epoch 的指标没有任何研究意义**：mAP50 ≈ 0.18 只证明"能跑"，**不能**写进论文当作实验结果，
   更不能说这是森林烟雾检测系统的性能。
4. 试跑样本仅 3,000 张（全量 15,069 张的 19.9%），训练轮数 2，**离可用模型还很远**。

## 五、必须提前说清的三个风险

1. **内存比显存紧张**：试跑期间系统可用内存一度只剩 **138.8 MB**。本机 15.6 GB 内存
   常驻占用约 83%，正式训练用 `workers=2` 时内存更吃紧。建议正式训练前关闭浏览器/QQ 等，
   或把 `workers` 降到 1。
2. **全量训练耗时预估**：按本次实测 ≈ 88 秒/epoch（375 iters）线性外推，
   全量 15,069 张 ≈ **7.4 分钟/epoch**（1,884 iters）＋每轮验证约 40 秒，
   即 **≈ 8 分钟/epoch**。50 epochs ≈ **6.5 小时**，30 epochs ≈ **4 小时**。
   这是估算，正式训练第一轮结束后应核对真实耗时再决定是否跑满。
3. **数据集场景不纯**：验证明细里能看到城市夜景、雪景湖泊、沙漠公路等画面，
   与"森林烟雾"并不吻合。论文里必须写明这一点，不能宣称"森林专用数据集"。
